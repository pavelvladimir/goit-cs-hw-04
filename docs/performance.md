# Порівняння швидкості

```bash
make benchmark
```

Порівнюю послідовний пошук, потоки та процеси на двох наборах:
128 файлів по 16 KiB і 8 файлів по 8 MiB. Використовую п'ять ключових слів,
зокрема Unicode та слово без збігів. Кожен результат звіряється з очікуваним словником,
який формується під час генерації даних, незалежно від алгоритму пошуку.

Після одного прогріву кожна конфігурація виконується п'ять разів; порядок запусків
циклічно змінюється. У таблиці наведено медіани. Час включає читання, пошук,
запуск і завершення виконавців, роботу менеджера Queue та об'єднання результатів.
Генерація файлів, перевірка результату й запис звіту не враховуються.
Файловий кеш прогрітий — це не вимірювання швидкості холодного диска.

## Результати

22.10.2026, macOS 26.5.2 ARM64, CPython 3.14.6 із GIL, 16 логічних CPU, `spawn`.
Кількість виконавців не включає службовий процес менеджера Queue.

| Спосіб | Виконавці | 128 × 16 KiB, мс | 8 × 8 MiB, мс |
| --- | --- | --- | --- |
| Послідовно | 1 | 11.498 | 152.450 |
| Потоки | 1 | 10.263 | 153.458 |
| Потоки | 2 | 11.414 | 159.214 |
| Потоки | 4 | 12.662 | 150.724 |
| Процеси | 1 | 145.143 | 296.286 |
| Процеси | 2 | 151.079 | 220.965 |
| Процеси | 4 | 147.527 | 180.222 |

На цих даних процеси не випередили послідовний пошук. Для великих файлів збільшення
кількості процесів допомогло, але запуск менеджера та обмін результатами все одно
коштували більше, ніж вдалося виграти. Потоки теж не дали стабільного прискорення.

Отже, більше виконавців не обов'язково означає швидше. Потоки можуть перекривати
очікування I/O, але GIL обмежує виконання Python-коду; процеси мають окремі інтерпретатори,
зате потребують запуску й серіалізації даних. На інших файлах або дисках результат
може відрізнятися.

Усі 70 вимірювань є в [benchmark.json](benchmark.json).
Новий запуск пише в `artifacts/benchmark.json`, не змінюючи збережений звіт.
Для короткої перевірки:

```bash
uv run --locked python -m scripts.benchmark --quick --repeats 1 --workers 1 2
```
